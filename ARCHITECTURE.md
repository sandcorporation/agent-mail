# Architecture and API reference

The Go HTTP server authenticates each request by hashing the bearer token (SHA-256) and comparing it in constant time with the hash stored in the `roles` row of the claimed role (seeded from `SWITCHBOARD_TOKENS` or added by registration); a row with `revoked_at` set refuses every request. That role is the sender identity and recipient authorization set. SQLite stores immutable message content plus recipient-specific state transitions in `role_states`; every view of a message (read, inbox, outbox, admin list, events, progress, metrics) takes its status from the recipient's row through `mail.StatusJoin`/`mail.StatusExpr`, so sender and recipient see the same status, and only the recipient's read changes it (`pending` → `read`); the database is mounted on a persistent volume. The CLI sends JSON over HTTPS/HTTP to the configured endpoint. The dashboard is served by the same process and treats message fields as text.

## State model

Messages carry a sender-chosen `priority` column (`normal` default, `urgent`), stored once and never changed. Databases created before priority existed gain the column on start (`ALTER TABLE ... DEFAULT 'normal'`, skipped when present), so existing mail reads as `normal`.

`pending` means newly delivered. Opening as recipient records `read`; `/ack` records `acknowledged`; `/complete` records `complete` (status filters also accept `completed`). Each is explicit and recipient scoped. Listing and watch have no state side effects. State is monotonic by intent but endpoints allow an explicit later state update; clients should use the furthest state reached.

## Delivery model

Every message receives a monotonically increasing SQLite ID. A client stores its cursor and polls `GET /api/watch?after=id`; server returns IDs greater than that cursor for the caller's role, or times out. The cursor is a global message ID, so it can safely skip unrelated roles' IDs. Clients may replay from an older cursor and see duplicates, and should dedupe by ID. No watcher claims or consumes an event. The watcher is not a session wake mechanism.

`GET /api/events` is the push form of the same model. A subscriber registers with an in-process hub for its role before it queries SQLite, so mail stored between the query and the wait still wakes it. A wake-up carries no data: the stream re-reads pending messages with an ID above its cursor, and SQLite remains the only source of truth. Each subscriber holds at most one queued wake-up, so a send never blocks on a slow or stalled stream and a coalesced wake-up still covers every stored message. Because the single SQLite connection commits IDs in order, the stream emits messages in ascending ID order and a client may resume with `Last-Event-ID` (the last message ID it received) without gaps; without a cursor it receives every message still `pending` for the role. Only messages still `pending` for the recipient are emitted. Event data is a summary (`id`, `sender`, `recipient`, `subject`, `priority`, `created_at`, optional `task_id`/`thread_id`, and `body` only for urgent mail); `priority` is the stored message priority and an urgent message's `body` is always present, even when empty. Keep-alive comments (`: ping`, `SWITCHBOARD_SSE_KEEPALIVE`, default 20s) keep idle connections open through reverse proxies; the HTTP server sets no write timeout, and shutdown (SIGINT/SIGTERM) ends every stream before the process exits. Subscribers are per process, which matches the single-writer SQLite deployment.

`GET /api/events/poll` is the same feed for clients that can only read a complete response. It shares the stream's cursor parsing and `mail.Service.pendingAfter` query, so the event objects and resume rules are identical. It also subscribes to the hub before its first query; if that query finds pending mail after the cursor it answers at once, otherwise it waits for a wake-up (then re-queries), the requested timeout (default 25s, capped by `SWITCHBOARD_POLL_MAX`, default 55s so it ends before a 60s proxy read timeout), client disconnect, or shutdown. The response carries the new cursor (last event ID, or the request cursor when empty), so a client loops `after=cursor` without gaps or repeats.

## Numbered slots

The `slots` table (`base`, `number`, `machine`, `directory`, `session_id`, `label`, `parent`, `registered_at`, `lease_until` in Unix milliseconds) has primary key `(base, number)` and unique key `(base, machine, directory)`, so one number has one holder and one identity holds one number per base. Register, takeover, heartbeat and release run in one transaction each over the single SQLite connection, so concurrent registrations are serialised. A row stays after its lease ends; that is how an identity whose number nobody took gets it back. A newcomer that picks an expired number deletes the old row. Time comes from the server clock (`Server.clock`, injectable in tests), and expiry is evaluated lazily in queries rather than by a sweeper, which lets presence heartbeats renew the same lease (see Presence).

Authentication resolves `X-Switchboard-Role` to a mailbox name: an exact role row as is; otherwise `<base>-N` with `<base>`'s token, where `-1` maps to `<base>`. Every handler, the event hub and the stored `recipient`/`sender`/`role_states.role` use that mailbox name, so the unnumbered base and slot 1 share mail, state and wake-ups without any data migration: existing mail addressed to a base role already is slot 1's mail. Slot membership is not checked on each request because the base token can claim any slot through `/api/slots` anyway; the boundary is the base, not the number.

## Presence

Presence lives on the slot row: `state`, `context_tokens` (-1 = never reported), `last_turn_at`, `reported_at` and `offline_noticed_at` (Unix ms, 0 = none) and `subagents` (running background sub-agents, 0 when a report leaves it out) are added to `slots` in place by `store.Init`, so databases from before presence keep their rows (shown with status `unknown` and no `reported_at`). Reports ride on the slot heartbeat rather than a separate endpoint because a report and a lease renewal are the same event: one request, one transaction, and no way for a session to be "present" without holding its number or vice versa. Offline therefore has a single definition, `lease_until <= now`, evaluated lazily like slot expiry, and the lease length is the heartbeat interval times the misses allowed (`SWITCHBOARD_SLOT_LEASE` overrides it). Takeover renumbers the displaced row in place so its presence moves with it.

Acting once per offline transition (for example telling the parent) needs no sweeper state beyond `offline_noticed_at`: `presence.Service.OfflineUnnoticed` lists sessions that went offline after reporting and have not been marked, and `presence.Service.MarkOfflineNoticed` marks one only if it has not renewed since it was read. Every report resets the mark, and a release sets it (an intended stop is not a stall). The stall sweeper (below) is their caller.

## Label addresses

A message to `label:<base>/<label>` is resolved inside the send transaction: if a leased slot of `<base>` carries the label, the row is inserted with that slot's mailbox as `recipient` and `addressed_to` set to the label address; otherwise it is inserted with the label address as `recipient`, `status = 'held'` and `held_at`. No principal can be named `label:…` (role names exclude `:`), so held mail is in no inbox, stream or poll. Register, heartbeat and takeover call `mail.DeliverHeld` in their own transaction after writing the slot row: every held message for `label:<base>/<slot label>` is given the slot's mailbox, status `pending`, `delivered_at`, and a new ID above every existing one (`held_id` keeps the old ID; `thread_id`/`reply_to`/`role_states` references follow, and `sqlite_sequence` is advanced). The new ID keeps the delivery model's promise that a cursor never has to look back. Because sends and slot changes are each one transaction on the single SQLite connection, a held message moves exactly once, to the first session that connects with the label, and a send racing a registration is either held and then moved or delivered directly. The hub is woken for the receiving mailbox after commit. `held_notice_at` records that the sender was told nobody connected (see stall notices); `idx_held` indexes held mail by `held_at`. The columns are added in place by `store.Init`, so older databases keep their mail unchanged.

Labels are scoped to a base because a base token can register any label for its own slots; the sender names the base, so a label can only ever be collected by sessions holding that base's token.

## Presence history and metrics

`slots` holds only the current state, so `presence_log(base, number, role, state, started_at, ended_at)` (Unix ms, `ended_at` NULL for the open row; added by `store.Init`, additive) keeps the stretches. `applyPresence` ends with `logPresenceReport`, which compares the slot's effective state (`unknown` when none was reported) with the open row and, only when they differ, closes it and opens a new one (`logPresenceState`). Going offline goes through `presence.LogOffline`: the sweep on a lapsed lease (at `lease_until`), a release, and the slot-row deletions in `freeNumber`, takeover and `displaceFirst`; a slot with no open row is left alone. Takeover's renumbering calls `movePresenceLog` so the displaced session's open state continues at its new number. The sweep prunes closed rows that ended more than 60 days ago (`presence.PruneLog`).

`presence.Service.Progress` (internal/presence/progress.go) builds the 진행 view served at `GET /api/progress` (boss roles) and `GET /api/admin/progress`. It reads no new table: live `slots` rows with the start of their open `presence_log` row, the newest mail per sender (`MAX(id)` per sender, so activity follows insertion order), the newest mail per sender to a boss mailbox, and open mail from boss senders (status from `role_states` first, as everywhere). Open directives (`openDirectives`) drop mail with `no_reply` (sent with `--no-reply`, or closed later by its sender or an admin through `mail.Service.Close`, which only sets that flag, so progress and the reminder sweep need no second rule) and mail replied to under `mail.Replies` (from the recipient's base to the sender's base, `reply_to` the directive or in its thread); the metrics first reply keeps the looser `mail.Answers` (also a shared `task_id` or a `#id` mention), so the two may differ on the same mail. Both rules are versioned by `mail.AnsweredRuleVersion` (internal/mail/answered.go, #233), pinned by the golden test `TestAnsweredRuleGolden`, which fails on any change to what either decides until the version is bumped. The one `answered_rule` row stores the version the stored directives were settled under; at start-up, before serving, the server runs `presence.Service.MigrateAnsweredRule`: no row (a new database, or one from before #233, which already ran version 1) stores the current version and marks nothing; an older stored version sets `no_reply` on every directive created before then that is open under the new rule, logs one line with the count and stores the new version. Services are the part of a mailbox name before the first `/`; a name is a boss when it or its base is in `SWITCHBOARD_BOSS_ROLES`.

`insight.Service.Metrics(days)` (internal/insight/metrics.go) builds the report served at `GET /api/metrics` (boss roles) and `GET /api/admin/metrics`. The parts are separate so the alert sweep can reuse them: `pendingAges(now, threshold)`, `currentSessionStates(now)`, `sessionStateTime(from, to)`, and the pure `firstReplies` / `threadRoundTrips` over `windowMail(from)`. Mail is grouped by base (`insight.BaseResolver`: `identity.BaseOf`, else the part before `-N`), so any numbered slot of a base answers for it. `created_at` is RFC 3339 text with a variable fraction, so the window is cut on parsed times rather than in SQL. Alert thresholds come from `insight.ParseThresholds` / `insight.Service.Limits()`.

## Stall notices

One goroutine started by `server.Run` calls `Server.sweep` (internal/server/stall.go) every `SWITCHBOARD_SWEEP_INTERVAL` (30s) and stops when the server's `done` channel closes; shutdown waits for it before closing the database. `sweep` is a plain function on the server clock so tests drive it directly. It sends four kinds of ordinary (`normal`) mail from the system sender `switchboard/system`:

- **Offline**: for each row from `OfflineUnnoticed`, one transaction sets `offline_noticed_at` (only if the row has not renewed since it was read) and, when that update hit, inserts the notice to the slot's `parent` (resolved like any recipient; none when the parent is empty, unknown, reserved or the session's own mailbox; those are only logged, by role name). The insert also carries an idempotency key `offline:<role>:<lease end>`.
- **Label**: held messages with `held_notice_at IS NULL` and `held_at` older than `SWITCHBOARD_LABEL_STALL` (10m) are grouped by sender and label address; one transaction per group sets `held_notice_at` on the messages it still finds held and unnoticed and inserts one notice listing their IDs. Held mail stays held and is still delivered when the label connects; later mail to the same label gets its own notice.
- **Metrics alerts** (alerts.go): `dueAlerts` checks `pendingAges` and `currentSessionStates` against `Limits()` (a zero limit skips the kind; offline sessions are not current). For each crossed `(kind, role)` one transaction inserts `alerts(kind, key, day, sent_at)` with primary key `(kind, key, day)` (`day` is the UTC date, `INSERT OR IGNORE`) and, when that insert hit, one mail per resolvable boss mailbox (`SWITCHBOARD_BOSS_ROLES`), `task_id` `alert:<kind>:<role>:<day>`, idempotency key that plus `:<boss mailbox>`. A pending alert skips a boss of the recipient's own base; when no boss is left, nothing is recorded, so it fires once one is configured. Rows older than 30 days are pruned by the sweep. The `alerts` table is added by `store.Init` (additive).
- **Directive reminders** (internal/presence/remind.go, #214): only with `SWITCHBOARD_REMIND=on`; off, `SweepReminders` returns before touching the database. The first sweep with it on inserts the one `remind_state` row (`INSERT OR IGNORE`, so off and on again keeps the first time). For each open directive with status `read`, a non-boss recipient and `created_at` not before that time, the reminder mail already stored (idempotency keys `remind:<id>:<n>`, `remind-sender:<id>`, read through the `UNIQUE(sender,idem)` index) is the schedule: the next reminder is due `SWITCHBOARD_REMIND_AFTER` × 2^n after the last one (or the directive), up to `SWITCHBOARD_REMIND_MAX`, then one notice to the directive's sender. The insert is `INSERT OR IGNORE` on that key, so repeated or concurrent sweeps and restarts send each once. A catch-up after downtime sends at most one per directive per sweep and keeps the gaps.

Marking and inserting in one transaction is what makes the sweep idempotent: repeated or concurrent sweeps send each notice once. The hub is woken for each recipient after commit.

The system sender is a reserved name, not a role row: `identity.Service.Authenticate` refuses `switchboard/system` and `switchboard/system-N` before looking up tokens (so an old database or `SWITCHBOARD_TOKENS` entry with that name grants nothing; `SWITCHBOARD_TOKENS` entries for it are skipped at start), `/api/register` answers 403 for it, and `identity.Mailbox` does not resolve it, so nobody can send mail to it or claim it as a parent or boss.

## Permission requests

`permissions` (created in place by `store.Init`) holds one row per request: an opaque server-issued `id` (`perm_` + 32 hex characters from `crypto/rand`), the requester's mailbox and base, `tool`, `summary`, the parent reported on the requester's active slot (`declared_parent`), the trusted `parent`/`parent_base`, `created_at`/`expires_at` (`SWITCHBOARD_PERMISSION_TTL`, 10m) and the answer (`decision`, `note`, `answered_by`, `answered_at`).

The parent is read once, in the request transaction, from the requester's active slot and fixed on the row, so a later heartbeat with another `parent` cannot redirect an open request. Because a session writes its own `parent` at registration and one base token covers every `<base>-N`, a parent of the requester's own base (itself or a sibling) is no independent check: it is kept only as `declared_parent` and ignored. Answers are accepted only from a role listed in `SWITCHBOARD_BOSS_ROLES` (a base or exact role), never from the requester's base, and authority is per base because the token is. The trusted parent can read the request but not answer it: sessions on one machine can read each other's profile files, so a worker could answer with its parent's role, while a boss credential lives on a separate machine. A request that nobody could answer (no registered boss of another base) is refused with 409 rather than left to expire, even when a parent exists.

The answer is one conditional `UPDATE … WHERE decision='' AND expires_at>now` in a transaction with the requester's notice, so concurrent answers produce one 200 and 409s; a request that matched no row is 409 when answered, 410 when expired. Checks run in the order 404 (unknown ID) → 403 (caller may not answer) → 409 → 410. New requests send urgent mail with the answer command to every boss of another base, and an informational urgent mail without the command to the trusted parent (unless the parent is itself a boss, which gets the answer mail); answers send urgent mail to the requester. Both carry the request ID as `task_id`.

Answering goes through one core, `asks.Service.AnswerPermission(ctx, id, by, decision, note, may)`, shared by the role endpoint (`may` = the boss check above) and the dashboard (`by="dashboard"`, `may` nil, still only while pending and unexpired).

## Question settings

`question_settings` (created in place by `store.Init`, which also inserts the `default` row once with everything off) holds one row per target: `default`, an exact role, or `<prefix>/*`. `watchers` is a JSON array. `asks.Service.ResolveQuestionSettings(role)` tries the role itself, then its base when it is `<base>-N`, then each `<prefix>/*` from the longest prefix down, then `default`, and returns the matched target with the values. Only the admin API reads and writes the table.

## Questions

`questions` (created in place by `store.Init`) holds one row per question: `id` (`q_` + 32 hex characters from `crypto/rand`), the asker's mailbox as authenticated (`asker`, possibly `<base>-N`) and `asker_base`, `questions` and `answers` as JSON, `status` (`pending`, `answered`, `withdrawn`), `answered_by` (a role, `dashboard`, or `panel` when the asker of an owner question answered from its session panel), `created_at`/`answered_at`/`withdrawn_at` (ms, 0 when unset), `seq`, and `answerer` (added in place; `owner` when no boss role of another base existed at ask time, so only a person answers it — on the dashboard or through the asker's exact role from its panel — else `''`), and `asker_machine`/`asker_directory`/`asker_label` (added in place; the live slot the question was asked from, empty without one). The answer goes to that session's live slot, else the newest live slot of the base with the same label, else it is held for the next matching session through `handoffs` (`internal/mail/handoff.go`: `message_id`, `base`, `machine`, `directory`, `label`; `DeliverHandoff` runs in the register/heartbeat transaction, so one session takes it). An answer delivered to a live slot keeps its `handoffs` row; each register/heartbeat first runs `presence.endLeases`, which holds again (`mail.HandOffUnread`) the unread answers in slots of that base whose lease has ended, before any number is reused or held mail is delivered. `seq` is one global change counter: create, answer and withdraw set it to `MAX(seq)+1` inside their transaction (writes are serialised by the single connection; a unique index backs that up), so `GET /api/questions/poll?after=` returns each changed question once in its current state. Every change wakes pollers through the mail hub on a topic that is not a role name. An index on `(status,answered_at)` serves the decision ledger (`internal/asks/decisions.go`), which reads answered rows as decisions; it has no table of its own.

Answering goes through one core, `(*Server).answerQuestion(ctx, id, by, answers)`, shared by the role endpoint and the dashboard (`by="dashboard"`, which skips the boss check but still requires `pending`). A role must be a boss (`SWITCHBOARD_BOSS_ROLES`) of a base other than `asker_base`, for the same reason as permission answers; the role endpoint refuses a role literally named `dashboard`. The load, checks (404 → 403 → 409 → 400 for bad answers), the conditional `UPDATE … WHERE status='pending'` and the mail run in one transaction, so concurrent answers produce one 200 and 409s. Withdraw is limited to the asker's base. Watchers are resolved from the asker's settings at the time of each mail. Bosses are not mailed on create; they poll.

## Security boundary

Bearer tokens grant one role and its numbered slots (`<role>-N`), unless a role is registered under that exact name. Only that role can act as sender, and only configured role names (directly, or through a label address of a configured base) may receive a message. Senders can inspect their own sent messages; any role may read the presence of every session (it holds no secrets); only recipients can update state or reply. Mailboxes of one base stay separate even though one token covers them: a request on a message of another mailbox of the caller's base (`team/worker` touching mail of `team/worker-2`) is refused with 403 naming the role to act as, so the body is never shown while the state stays unchanged; mail of other bases stays 404. The dashboard holds no role token. Admin access is denied unless `SWITCHBOARD_ADMIN_AUTH` is set; with `builtin`, an admin signs in with name, argon2id-hashed password and TOTP and gets an `HttpOnly`, `SameSite=Strict` session cookie whose id is stored only as a hash (`admin_sessions`, 12 h sliding). Every mode ends in that session, so later modes only add the sign-in step. Under the transition rule (mode unset, `SWITCHBOARD_ADMIN_PROXY_TOKEN` set) an authenticating reverse proxy (for example Authelia in front of nginx) injects the server-held `X-Switchboard-Admin` secret on `/api/admin/*` instead. Because both authenticate by cookie, every admin write (`PUT`, `POST`, `DELETE`) must also carry `Content-Type: application/json` and `X-Switchboard-Dashboard: 1`, and must not come with a `Sec-Fetch-Site` other than `same-origin`; otherwise it gets 403. The custom header forces a CORS preflight, which a cross-site page cannot pass. Deploy behind a private interface or private reverse proxy with TLS when traffic leaves a trusted host network.

Terminal hosting (#173) is compiled in but off: only `SWITCHBOARD_HOSTING=on` turns it on, and while off every hosting route (`/api/admin/terminals…`, `/api/admin/nodes…`, `/api/node/…`) answers exactly like an unknown route. With it on, the server refuses to start unless `LISTEN_ADDR` is loopback (`127.0.0.0/8`, `::1`, `localhost`; `:8080` is not), `SWITCHBOARD_ADMIN_AUTH` is `builtin` or `oidc`, and `DB_PATH` names a database other than the container default `/data/mail.db`. `GET /api/admin/me` reports `hosting`.

With hosting on, `GET`/`POST /api/admin/terminals` and `PUT`/`DELETE /api/admin/terminals/{id}` list, create, change and delete `hosted_sessions` records (admin sign-in, write guard on writes); `GET /api/admin/nodes` lists the `nodes` registry (never the token hash) and `DELETE /api/admin/nodes/{name}` revokes a node (404 for an unknown one): its socket closes at once (the hub also drops any attached node found revoked at its 2 s sync), its token is refused from then on (401), and its records show `node offline`. A record may name only a registered, unrevoked node (400 otherwise). A record has an id `hs_` + 32 hex, an agent session UUID made at create, `restart` (`always` default, `on-failure`, `never`) and `desired` (`running` default, `stopped`); `(node, base, directory)` is unique (409). Create refuses (400, naming the field) a base that is not a registered role, a directory that is not absolute (`/…`, `C:\…`, `\\server\share…`), agent args `--session-id`, `--resume`/`-r`, `--continue`/`-c`, `--print`/`-p`, and env names containing `TOKEN`, `SECRET`, `KEY` or `PASSWORD`. Every record carries `runtime` (`state`, `since`, `pid`, `run`, `restarts`, `last_exit`, `next_attempt_at`, `resume_failed`): `unknown` until its node reports, `node offline` while a registered node is detached. `POST /api/admin/terminals/{id}/restart` restarts a running session with resume through its node (409 while the node is offline) and starts a stopped one; `POST /api/admin/terminals/{id}/new-conversation` gives the record a new agent session id (`launched` back to 0, `desired=running`), and its node stops the session and starts it with `--session-id`. Both are record changes, `restart_gen` (Restart) and `start_gen` (every set to `running`) counters and the agent session id, so a node acts on them at its next `assign` and the CLI needs no server. `switchboard host add|list|set|start|stop|restart|new-conversation|remove` edits the same records directly in `DB_PATH` (refused when unset or the container default): `host add --node N --base ROLE --profile P --dir PATH [--label] [--parent] [--restart] [--ask-permissions] -- <agent args>`; `start`/`stop` set `desired`; `host set ID --skip-permissions on|off` changes `skip_permissions`. Permission mode (#220): `skip_permissions` (1 for new records unless `--ask-permissions` or `"skip_permissions":false`, 0 for records migrated from before) makes `node.Config.Argv` add the agent's permission-skip arguments from `permissionSkip` (keyed by the agent's file name; `claude`: `--dangerously-skip-permissions --settings {"skipDangerousModePermissionPrompt":true}`) after the session flag, unless the record's args already choose a permission mode; an unknown agent gets nothing. It applies at the next launch. `switchboard node invite NAME` (against `DB_PATH`, the same refusals as `host`) prints a one-time code `sbj_…` valid 15 minutes; `node_invites` keeps only its hash, and a new code for the same name replaces an unused one. A registered name, live or revoked, cannot be invited. `POST /api/node/join` with `{"code":…}` spends the code once (401 when unknown, used or expired) and answers the node's name and a new token `sbn_…`, which the `nodes` row keeps only as a hash. `switchboard node --host URL --join CODE [--token-file PATH]` does that exchange and writes the token (default `node.token` in the client config directory; mode 0600 in a 0700 directory, a protected user-only DACL on Windows; an existing file is never replaced), then runs the node. The hosting tables are created empty by `store.Init` and only hosting reads them.

`switchboard up --data DIR --port PORT [--node NAME]` runs the server with hosting on, `LISTEN_ADDR=127.0.0.1:PORT` and `DB_PATH=DIR/switchboard.db`, and a node (default name `local`) in the same process; every hosting refusal still applies. It binds its listener before the node's backend (tmux server, keeper) starts: when the port is held, even by a socket that only bound it, `up` exits non-zero at once with `up: listen tcp …: bind: …` and leaves no keeper or tmux server. On first start it writes the node token to `DIR/node.token` (mode 0600; the `nodes` row keeps only its hash). The node attaches over loopback HTTP exactly as `switchboard node --host URL --token-file PATH` does (loopback hosts only; another host is refused naming the access-scope decision of #173): one WebSocket `GET /api/node/socket` with `Authorization: Bearer <node token>`; a node token authorises nothing else (mail, role and admin routes answer 401). Frames are JSON `wire.NodeFrame`: host → node `assign` (the node's full record list, on attach and after every change) and `restart`; node → host `hello` (name, machine, OS, version, backend), `state` (per record: runtime and whether its conversation was launched, which the host stores as `launched` only while the record still holds that conversation) and `notice` (below). The host re-reads the records every 2 s, so a `host` CLI change reaches the node, and publishes the live kind `terminals` on record and state changes. The node does not reconcile before its first `assign`; while detached it keeps enforcing the last one and reconnects after 1 s, doubling to 30 s. Its tmux server is `switchboard-n<12 hex of the token file path>` (logged at start), so sessions outlive `up` and the next `up` adopts them without relaunching. On Windows (10 1809 or later) the sessions live in the keeper on pipe `switchboard-keeper-n<same hex>` (log `keeper-<instance>.log` in the data directory, or the user cache directory for `node`); a keeper of this version is adopted the same way, one of another version is replaced and every session resumes. On other OSes the node refuses to start. `switchboard node --restart-sessions` stops every `sb-` session at start (grace 10 s) so each record relaunches with `--resume` after the first `assign`. The dashboard's 터미널 tab and the 노드 list in 설정 (with 끊기 = revoke) appear only when `/api/admin/me` reports `hosting`. The operations instance never sets it: a test (`internal/config`) fails if `compose.yaml`, `Jenkinsfile`, `Dockerfile`, a workflow or a deploy env file names any `SWITCHBOARD_HOSTING*` setting.

Restart rules (#188, node side, clock injected): an exit restarts by policy (`never` stops; `on-failure` stops on exit 0). A relaunch waits 2 s, doubling per consecutive short run up to 5 min (`backing off`, `next_attempt_at`); a run of 10 min or longer resets the backoff and the crash-loop count. Five short runs (each under 10 min) within 30 min are a `crashloop`: no more attempts until Start (`start_gen`) or Restart (`restart_gen`). A `--resume` run that exits non-zero within 15 s twice in a row is a missing conversation: the node waits (`resume failed`) and sends a `notice`; the host replaces the record's agent session id once (only while it still holds the failed one, `launched` = 0), and the node starts it with `--session-id` at once, reporting `resume_failed` for that conversation. Never `--continue`. A node sends each held notice once per connection, again after reconnecting; the host mails it through the server's `Notify` (system mail from `switchboard/system`) to the record's `parent`, or to every `SWITCHBOARD_BOSS_ROLES` role without one, with idempotency key `hosting:crashloop:<id>:<run>` or `hosting:resumefail:<id>:<run>` (`:<mailbox>` appended when there are several recipients), so a repeated notice sends nothing. A terminal holder that is gone (tmux server killed, keeper replaced) leaves no sessions, and every record that should run is launched again at once with `--resume`. The 터미널 tab shows 재시도 대기 with the time left, 반복 실패, 재개 실패 and 새 대화(재개 실패), and 새 대화 behind a confirm.

Session cap and subscription limit (#190). Cap: the node runs at most `SWITCHBOARD_HOSTING_MAX` sessions (default 4, read by `node.Resolve`, reported in its hello as `max` and kept in `nodes.max_sessions`). The host refuses (409, `hosting.CapacityError`; the CLI prints the same message) a create with `desired=running`, and a start, restart or new conversation of a stopped record, when the node already has that many records set to run. The node is the backstop: a record beyond the cap (cap lowered, a backed-off record whose wait ended) is `waiting` and starts oldest-created first when a live session stops; stopped, backing-off and crash-loop records hold no slot, and nothing running is stopped for the cap. Class: `hosted_sessions.class` is `lead`, `coordinator`, `execute` (default) or `review` (API `class`, `host add --class`, the Add form). Limit: every 5 s (`node.LimitScan`) the node reads each live session's visible screen and matches the agent's usage-limit message (`node.limitPatterns`, the one list; `node.ParseReset` reads `resets 3pm (Zone)`, `resets Nov 21, 5pm`, `reset at 10:30pm`, `|<unix>`); its state frames carry `limit` (`since`, `reset_at`), stored in `nodes.limit_since`/`limit_reset`. A showing ends when the screen no longer shows the message, and is spent (ignored while it stays on screen) once its reset time passes. The operator sets or clears the limit with `PUT /api/admin/terminals/limit {"limited":…}`, `switchboard host limit on|off` or the tab's toggle (`hosting_limit` row); off also ignores every showing that began before it. `GET /api/admin/terminals/limit` (and `host limit`) answers `limited`, `source` (`operator`, `screen`), `since`, `reset_at`, `cleared_at`. While limited no session is stopped or relaunched for it; records of class `execute` and `review` report `accepting_work: false` (lead and coordinator stay `true`). That flag is the whole of "takes no new work items" here: mail, questions and permission requests reach every session as before (inbox and watch stay non-consuming, so nothing is held or sent twice); the work-item dispatcher (#174) must not hand an item to a record whose `accepting_work` is false. When the limit clears the hub records `cleared_at` and publishes the live kind `limit-cleared` once (with `terminals`); `hosting.ResumeOrder` sorts work items queued while limited before new ones, which #174 uses on that change.

Slot tie-in (#189): the node never registers slots; the switchboard plugin inside a hosted session registers `(base, machine, directory, session_id)` as a hand-launched one does, and because machine and directory stay the same across relaunches it gets its number back (`presence` is unchanged). The server hands the hub `SlotOf(base, machine, directory)` (presence's `FolderSlot`, read only: the slot at the node's machine in the record's directory or its session-marked form `<dir> #<8 hex>`, a leased one first, then the one heard from last). `GET /api/admin/terminals` adds `slot` (`role`, `directory`, `session_id`, `lease_until`, `online`) and `presence`: `online` while the lease runs, `offline (process alive)` when it ended with the process running (left to the existing offline notices; the node does not act on it), `offline` otherwise. Conversation following: at each sync, a launched record running on an attached node whose slot is leased, was heard from at or after the host first saw the current run (so a slot the previous process left never counts), and reports a valid UUID other than the record's `agent_session_id` takes that id and keeps `launched` = 1; the node, seeing a changed id with `launched` on both sides, keeps the process and resumes the new id at the next launch (a changed id with `launched` = 0 is still a new conversation that replaces the process). The 터미널 tab's 이름 column shows the slot role and its 상태 column the presence; the 세션 tab adds a 터미널 link to a session a hosted record holds, opening the record's detail (`#terminals/<id>/screen`; an older `#terminal=<id>` link turns into it), and the session's own 터미널 sub-tab shows the same live screen.

Browser terminal view (#191, hosting on): `POST /api/admin/terminals/{id}/ticket {"mode":"view"|"input"}` (admin sign-in, write guard) returns a ticket of 32 random bytes, kept in host memory only as its SHA-256, single use, valid 30 s, bound to the record and to the admin's sign-in (the hash of the session cookie). `GET /api/admin/terminals/{id}/socket?ticket=…` needs the same sign-in (401), an `Origin` passing the `/api/admin/live` rule (403) and that ticket (403 when missing, used, expired, or issued for another record or sign-in). It sends a text `{"type":"hello","state":…,"cols":C,"rows":R}`, then binary frames (a snapshot, then output), and `{"type":"state",…}` when the record's state changes (`gone` once deleted); it re-checks the sign-in every 30 s and closes with 1008 `signed out`. Each viewer has a 256-frame queue; a full one drops it (1013 `too slow`, or the socket is cut a second later if the write is stuck) and the page reconnects with a new ticket to a fresh snapshot. The hub sends the node `attach` for every new viewer and `detach` when the last one leaves; the node then streams that terminal (`term.Backend.Stream`) as binary frames `wire.EncodeTermFrame` (`s` snapshot = `Grid.Snapshot` with up to 2000 history lines, taken after the stream opened; `o` output), and resends a snapshot when the session ends (tmux can drop the last output from the stream but not the screen) and when the stream reopens after a relaunch. Without a viewer no stream is open and only JSON crosses the channel. The page loads the terminal files only from the list `/api/admin/me` returns with hosting on (`terminal_assets`); `/assets/…` answers like an unknown path with hosting off, and the CSP is unchanged.

Terminal input (#192): a socket opened with an `input` ticket takes text frames `{"type":"input","data":"<utf-8>"}` and `{"type":"resize","cols":C,"rows":R}` (1–500 x 1–200); a `view` socket reads and drops every frame. Input over 64 KiB (`hosting.MaxInput`, the page splits pastes into 32 KiB frames) and a bad frame get `{"type":"refused","error":…}` and the socket stays open. The hub relays the node `input` (`Data`, bytes) and `resize` (`Cols`, `Rows`) frames; the node types them in its read loop, so input keeps its order, with `term.Backend.Input` / `Resize`. Input waits up to 2 s for room on the node channel and is refused rather than dropping the node. One size per terminal: the last viewer that sent input or a resize sets it. A resize applies at once; input from a viewer other than the one whose size the terminal has first resizes it to that viewer's last size. A changed size is stored in `hosted_sessions.cols/rows` (used on the next launch) and sent to the other viewers as `{"type":"size","cols":C,"rows":R}`; a page in View mode follows it, a page in Type mode fits its panel (xterm.js fit addon) and sends its own size after every hello and panel resize. Every socket writes `terminal_log(id, session, admin_user, kind, at, bytes)` rows: `attach` on open, `detach` on close, `input` with the byte count per socket per minute (written when the next minute's input arrives, at the 30 s re-check, or on close). Input content is never stored. The sweep deletes rows older than 30 days (`hosting.PruneLog`), hosting on or off. `GET /api/admin/terminals/{id}/log` returns the newest 100 rows, shown under the terminal view.

## Invites

`internal/identity/invites.go` holds invites and join; scope and boss decisions are in groups.go of the same package. `createInvite` runs in one transaction: it reads the prefix's group, and when there is none it refuses (409) if any role already sits under `<prefix>/` (a new group would turn those internal roles into group roles with less access), else inserts the group; then it inserts the invite with `store.TokenHash` of the normalized code (upper case, no dashes or spaces). The group cache is reloaded after a created group. `Join` checks the code, the group (live), the role (the invite's role, under the prefix and in no deeper group) and inserts the role with the token hash and marks the invite used in one transaction, so a code cannot be spent twice. Dead codes (unknown, used, cancelled, expired) share one 410 and feed a per-IP `adminauth.Limiter` (`Server.joinLimits`). `revokeGroup` cancels the group's open invites. The CLI `join` claims the profile file with `O_EXCL` (mode 0600) before calling the server, so a taken name fails before the code is spent, and removes it if the join fails.

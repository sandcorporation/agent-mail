# Architecture and API reference

The Go HTTP server authenticates each request by constant-time comparison against the configured `AGENT_MAIL_TOKENS` role/token map. That role is the sender identity and recipient authorization set. SQLite stores immutable message content plus recipient-specific state transitions in `role_states`; the database is mounted on a persistent volume. The CLI sends JSON over HTTPS/HTTP to the configured endpoint. The dashboard is served by the same process and treats message fields as text.

## State model

Messages carry a sender-chosen `priority` column (`normal` default, `urgent`), stored once and never changed. Databases created before priority existed gain the column on start (`ALTER TABLE ... DEFAULT 'normal'`, skipped when present), so existing mail reads as `normal`.

`pending` means newly delivered. Opening as recipient records `read`; `/ack` records `acknowledged`; `/complete` records `complete` (status filters also accept `completed`). Each is explicit and recipient scoped. Listing and watch have no state side effects. State is monotonic by intent but endpoints allow an explicit later state update; clients should use the furthest state reached.

## Delivery model

Every message receives a monotonically increasing SQLite ID. A client stores its cursor and polls `GET /api/watch?after=id`; server returns IDs greater than that cursor for the caller's role, or times out. The cursor is a global message ID, so it can safely skip unrelated roles' IDs. Clients may replay from an older cursor and see duplicates, and should dedupe by ID. No watcher claims or consumes an event. The watcher is not a session wake mechanism.

`GET /api/events` is the push form of the same model. A subscriber registers with an in-process hub for its role before it queries SQLite, so mail stored between the query and the wait still wakes it. A wake-up carries no data: the stream re-reads pending messages with an ID above its cursor, and SQLite remains the only source of truth. Each subscriber holds at most one queued wake-up, so a send never blocks on a slow or stalled stream and a coalesced wake-up still covers every stored message. Because the single SQLite connection commits IDs in order, the stream emits messages in ascending ID order and a client may resume with `Last-Event-ID` (the last message ID it received) without gaps; without a cursor it receives every message still `pending` for the role. Only messages still `pending` for the recipient are emitted. Event data is a summary (`id`, `sender`, `recipient`, `subject`, `priority`, `created_at`, optional `task_id`/`thread_id`, and `body` only for urgent mail); `priority` is the stored message priority and an urgent message's `body` is always present, even when empty. Keep-alive comments (`: ping`, `AGENT_MAIL_SSE_KEEPALIVE`, default 20s) keep idle connections open through reverse proxies; the HTTP server sets no write timeout, and shutdown (SIGINT/SIGTERM) ends every stream before the process exits. Subscribers are per process, which matches the single-writer SQLite deployment.

`GET /api/events/poll` is the same feed for clients that can only read a complete response. It shares the stream's cursor parsing and `pendingAfter` query, so the event objects and resume rules are identical. It also subscribes to the hub before its first query; if that query finds pending mail after the cursor it answers at once, otherwise it waits for a wake-up (then re-queries), the requested timeout (default 25s, capped by `AGENT_MAIL_POLL_MAX`, default 55s so it ends before a 60s proxy read timeout), client disconnect, or shutdown. The response carries the new cursor (last event ID, or the request cursor when empty), so a client loops `after=cursor` without gaps or repeats.

## Security boundary

Bearer tokens grant one role. Only that role can act as sender, and only configured role names may receive a message. Senders can inspect their own sent messages; only recipients can update state or reply. The dashboard token is held in browser local storage; use a trusted browser profile and private network. Deploy behind a private interface or private reverse proxy with TLS when traffic leaves a trusted host network.

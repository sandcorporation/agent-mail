# Architecture and API reference

The Go HTTP server authenticates each request by constant-time comparison against the configured `AGENT_MAIL_TOKENS` role/token map. That role is the sender identity and recipient authorization set. SQLite stores immutable message content plus recipient-specific state transitions in `role_states`; the database is mounted on a persistent volume. The CLI sends JSON over HTTPS/HTTP to the configured endpoint. The dashboard is served by the same process and treats message fields as text.

## State model

Messages carry a sender-chosen `priority` column (`normal` default, `urgent`), stored once and never changed. Databases created before priority existed gain the column on start (`ALTER TABLE ... DEFAULT 'normal'`, skipped when present), so existing mail reads as `normal`.

`pending` means newly delivered. Opening as recipient records `read`; `/ack` records `acknowledged`; `/complete` records `complete` (status filters also accept `completed`). Each is explicit and recipient scoped. Listing and watch have no state side effects. State is monotonic by intent but endpoints allow an explicit later state update; clients should use the furthest state reached.

## Delivery model

Every message receives a monotonically increasing SQLite ID. A client stores its cursor and polls `GET /api/watch?after=id`; server returns IDs greater than that cursor for the caller's role, or times out. The cursor is a global message ID, so it can safely skip unrelated roles' IDs. Clients may replay from an older cursor and see duplicates, and should dedupe by ID. No watcher claims or consumes an event. The watcher is not a session wake mechanism.

`GET /api/events` is the push form of the same model. A subscriber registers with an in-process hub for its role before it queries SQLite, so mail stored between the query and the wait still wakes it. A wake-up carries no data: the stream re-reads pending messages with an ID above its cursor, and SQLite remains the only source of truth. Each subscriber holds at most one queued wake-up, so a send never blocks on a slow or stalled stream and a coalesced wake-up still covers every stored message. Because the single SQLite connection commits IDs in order, the stream emits messages in ascending ID order and a client may resume with `Last-Event-ID` (the last message ID it received) without gaps; without a cursor it receives every message still `pending` for the role. Only messages still `pending` for the recipient are emitted. Event data is a summary (`id`, `sender`, `recipient`, `subject`, `priority`, `created_at`, optional `task_id`/`thread_id`, and `body` only for urgent mail); `priority` is the stored message priority and an urgent message's `body` is always present, even when empty. Keep-alive comments (`: ping`, `AGENT_MAIL_SSE_KEEPALIVE`, default 20s) keep idle connections open through reverse proxies; the HTTP server sets no write timeout, and shutdown (SIGINT/SIGTERM) ends every stream before the process exits. Subscribers are per process, which matches the single-writer SQLite deployment.

`GET /api/events/poll` is the same feed for clients that can only read a complete response. It shares the stream's cursor parsing and `pendingAfter` query, so the event objects and resume rules are identical. It also subscribes to the hub before its first query; if that query finds pending mail after the cursor it answers at once, otherwise it waits for a wake-up (then re-queries), the requested timeout (default 25s, capped by `AGENT_MAIL_POLL_MAX`, default 55s so it ends before a 60s proxy read timeout), client disconnect, or shutdown. The response carries the new cursor (last event ID, or the request cursor when empty), so a client loops `after=cursor` without gaps or repeats.

## Numbered slots

The `slots` table (`base`, `number`, `machine`, `directory`, `session_id`, `label`, `parent`, `registered_at`, `lease_until` in Unix milliseconds) has primary key `(base, number)` and unique key `(base, machine, directory)`, so one number has one holder and one identity holds one number per base. Register, takeover, heartbeat and release run in one transaction each over the single SQLite connection, so concurrent registrations are serialised. A row stays after its lease ends; that is how an identity whose number nobody took gets it back. A newcomer that picks an expired number deletes the old row. Time comes from the server clock (`Server.clock`, injectable in tests), and expiry is evaluated lazily in queries rather than by a sweeper, which lets presence heartbeats renew the same lease (see Presence).

Authentication resolves `X-Agent-Mail-Role` to a mailbox name: an exact role row as is; otherwise `<base>-N` with `<base>`'s token, where `-1` maps to `<base>`. Every handler, the event hub and the stored `recipient`/`sender`/`role_states.role` use that mailbox name, so the unnumbered base and slot 1 share mail, state and wake-ups without any data migration: existing mail addressed to a base role already is slot 1's mail. Slot membership is not checked on each request because the base token can claim any slot through `/api/slots` anyway; the boundary is the base, not the number.

## Presence

Presence lives on the slot row: `state`, `context_tokens` (-1 = never reported), `last_turn_at`, `reported_at` and `offline_noticed_at` (Unix ms, 0 = none) are added to `slots` in place by `initSchema`, so databases from before presence keep their rows (shown with status `unknown` and no `reported_at`). Reports ride on the slot heartbeat rather than a separate endpoint because a report and a lease renewal are the same event: one request, one transaction, and no way for a session to be "present" without holding its number or vice versa. Offline therefore has a single definition, `lease_until <= now`, evaluated lazily like slot expiry, and the lease length is the heartbeat interval times the misses allowed (`AGENT_MAIL_SLOT_LEASE` overrides it). Takeover renumbers the displaced row in place so its presence moves with it.

Acting once per offline transition (for example telling the parent) needs no sweeper state beyond `offline_noticed_at`: `Server.offlineUnnoticed` lists sessions that went offline after reporting and have not been marked, and `Server.markOfflineNoticed` marks one only if it has not renewed since it was read. Every report resets the mark, and a release sets it (an intended stop is not a stall). The stall sweeper (below) is their caller.

## Label addresses

A message to `label:<base>/<label>` is resolved inside the send transaction: if a leased slot of `<base>` carries the label, the row is inserted with that slot's mailbox as `recipient` and `addressed_to` set to the label address; otherwise it is inserted with the label address as `recipient`, `status = 'held'` and `held_at`. No principal can be named `label:…` (role names exclude `:`), so held mail is in no inbox, stream or poll. Register, heartbeat and takeover call `deliverHeld` in their own transaction after writing the slot row: every held message for `label:<base>/<slot label>` is given the slot's mailbox, status `pending`, `delivered_at`, and a new ID above every existing one (`held_id` keeps the old ID; `thread_id`/`reply_to`/`role_states` references follow, and `sqlite_sequence` is advanced). The new ID keeps the delivery model's promise that a cursor never has to look back. Because sends and slot changes are each one transaction on the single SQLite connection, a held message moves exactly once, to the first session that connects with the label, and a send racing a registration is either held and then moved or delivered directly. The hub is woken for the receiving mailbox after commit. `held_notice_at` records that the sender was told nobody connected (see stall notices); `idx_held` indexes held mail by `held_at`. The columns are added in place by `initSchema`, so older databases keep their mail unchanged.

Labels are scoped to a base because a base token can register any label for its own slots; the sender names the base, so a label can only ever be collected by sessions holding that base's token.

## Stall notices

One goroutine started by `runServer` calls `Server.sweep` every `AGENT_MAIL_SWEEP_INTERVAL` (30s) and stops when the server's `done` channel closes; shutdown waits for it before closing the database. `sweep` is a plain function on the server clock so tests drive it directly. It sends two kinds of ordinary (`normal`) mail from the system sender `agent-mail/system`:

- **Offline**: for each row from `offlineUnnoticed`, one transaction sets `offline_noticed_at` (only if the row has not renewed since it was read) and, when that update hit, inserts the notice to the slot's `parent` (resolved like any recipient; none when the parent is empty, unknown, reserved or the session's own mailbox; those are only logged, by role name). The insert also carries an idempotency key `offline:<role>:<lease end>`.
- **Label**: held messages with `held_notice_at IS NULL` and `held_at` older than `AGENT_MAIL_LABEL_STALL` (10m) are grouped by sender and label address; one transaction per group sets `held_notice_at` on the messages it still finds held and unnoticed and inserts one notice listing their IDs. Held mail stays held and is still delivered when the label connects; later mail to the same label gets its own notice.

Marking and inserting in one transaction is what makes the sweep idempotent: repeated or concurrent sweeps send each notice once. The hub is woken for each recipient after commit.

The system sender is a reserved name, not a role row: `authenticate` refuses `agent-mail/system` and `agent-mail/system-N` before looking up tokens (so an old database or `AGENT_MAIL_TOKENS` entry with that name grants nothing; `AGENT_MAIL_TOKENS` entries for it are skipped at start), `/api/register` answers 403 for it, and `mailbox` does not resolve it, so nobody can send mail to it or claim it as a parent or boss.

## Permission requests

`permissions` (created in place by `initSchema`) holds one row per request: an opaque server-issued `id` (`perm_` + 32 hex characters from `crypto/rand`), the requester's mailbox and base, `tool`, `summary`, the parent reported on the requester's active slot (`declared_parent`), the trusted `parent`/`parent_base`, `created_at`/`expires_at` (`AGENT_MAIL_PERMISSION_TTL`, 10m) and the answer (`decision`, `note`, `answered_by`, `answered_at`).

The parent is read once, in the request transaction, from the requester's active slot and fixed on the row, so a later heartbeat with another `parent` cannot redirect an open request. Because a session writes its own `parent` at registration and one base token covers every `<base>-N`, a parent of the requester's own base (itself or a sibling) is no independent check: it is kept only as `declared_parent` and ignored. Answers are accepted only from a role listed in `AGENT_MAIL_BOSS_ROLES` (a base or exact role), never from the requester's base, and authority is per base because the token is. The trusted parent can read the request but not answer it: sessions on one machine can read each other's profile files, so a worker could answer with its parent's role, while a boss credential lives on a separate machine. A request that nobody could answer (no registered boss of another base) is refused with 409 rather than left to expire, even when a parent exists.

The answer is one conditional `UPDATE … WHERE decision='' AND expires_at>now` in a transaction with the requester's notice, so concurrent answers produce one 200 and 409s; a request that matched no row is 409 when answered, 410 when expired. Checks run in the order 404 (unknown ID) → 403 (caller may not answer) → 409 → 410. New requests send urgent mail with the answer command to every boss of another base, and an informational urgent mail without the command to the trusted parent (unless the parent is itself a boss, which gets the answer mail); answers send urgent mail to the requester. Both carry the request ID as `task_id`.

## Security boundary

Bearer tokens grant one role and its numbered slots (`<role>-N`), unless a role is registered under that exact name. Only that role can act as sender, and only configured role names (directly, or through a label address of a configured base) may receive a message. Senders can inspect their own sent messages; any role may read the presence of every session (it holds no secrets); only recipients can update state or reply. Mailboxes of one base stay separate even though one token covers them: a request on a message of another mailbox of the caller's base (`team/worker` touching mail of `team/worker-2`) is refused with 403 naming the role to act as, so the body is never shown while the state stays unchanged; mail of other bases stays 404. The dashboard holds no token: an authenticating reverse proxy (for example Authelia in front of nginx) injects the server-held `X-Agent-Mail-Admin` secret on `/api/admin/*`, and the browser stores nothing. Deploy behind a private interface or private reverse proxy with TLS when traffic leaves a trusted host network.

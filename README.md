# Agent Mail

Agent Mail is a small self hosted mailbox for stable, role addressed agent identities. The service owns the identity boundary and durable message store; identities such as `sandcorp/boss` or `codemit/worker-1` are configured roles, not Orca session or terminal handles. A role keeps the same inbox after an agent session restarts.

Why we built it: [A role mailbox for AI sessions](https://sandcorp.co.kr/blog/role-mailbox-for-ai-sessions). Made by [Sandcorp](https://sandcorp.co.kr).

## Design decisions

- Go service and CLI share one module; SQLite is local to the service and persisted on a named Docker volume. SQLite keeps deployment small and avoids a separate database service.
- Every API call uses a bearer credential mapped server side to exactly one role. Existing `AGENT_MAIL_TOKENS=role=token,...` deployments are imported into SQLite at startup. New roles can enroll at runtime when the operator sets an external `AGENT_MAIL_ENROLLMENT_TOKEN`; senders cannot impersonate another sender, and recipients must be registered roles.
- The dashboard is an administrator view of all roles and mailboxes. Its only writes are question answers and question settings. It uses same-origin requests and never receives role credentials; message and question content is rendered as text.
- Watch is durable long polling. The cursor is the last delivered global message ID. Multiple watchers can replay from the same cursor and receive duplicate notifications; consumers should deduplicate by message ID. A watch only reports new mail; it does not mark mail read or wake a stopped LLM.

## Message and status semantics

Messages have sender, recipient, subject, markdown or plain text body, UTC timestamp, optional task ID, thread ID, and reply-to ID, and a priority: `normal` (the default) or `urgent`. Any role may send urgent mail; priority changes how mail is shown and streamed (urgent event frames include the body), not who may read it. The server stores urgent bodies in full; clients that show them inline choose their own length limit. New recipient messages are `pending`. Opening with `read` marks the message `read`; `ack` explicitly accepts responsibility and stores `acknowledged`; `complete` records finished work. These are recipient-side states. Inbox listing and watch do not consume or mutate messages. Outbox lists messages authored by the current role. Search matches subject, body, and task ID; the service returns at most 100 newest matches.

A thread's root ID is shared in `thread_id`; `reply_to` points at the immediate parent. Idempotency keys are unique per sender and key. A retry with the same key returns the original message and does not create a second one. Keep a key stable for retries of one logical send and use a fresh key for a new message.

## Build and run locally

Requires Go 1.24+ for development. End users install a compiled release binary and do not need Go. Create distinct random tokens per role and set them in the environment (never commit token values):

```sh
export AGENT_MAIL_TOKENS='sandcorp/boss=REPLACE_WITH_RANDOM,codemit/coordinator=REPLACE_WITH_RANDOM,codemit/worker-1=REPLACE_WITH_RANDOM'
export DB_PATH="$PWD/mail.db"
go run ./cmd/agent-mail
```

The service listens on `:8080` by default. Visit `http://localhost:8080`. Health endpoint: `/health`.

Configure a CLI (read the token from a protected file; the token is stored with user-only file permissions):

```sh
agent-mail config set --endpoint http://localhost:8080 --role codemit/worker-1 --token-file /path/to/role-token
agent-mail --profile codemit-worker config set --endpoint http://localhost:8080 --role codemit/worker-1 --token-file /path/to/role-token
agent-mail send --to codemit/coordinator --subject 'Build ready' --task task-123 --body-file report.md --idempotency-key task-123-report
cat report.md | agent-mail send --to codemit/coordinator --subject 'Build ready' --body-file /dev/stdin
agent-mail inbox [--q term] [--status pending|read|acknowledged|complete] [--json]
agent-mail outbox --json
agent-mail read 42
agent-mail reply 42 --subject 'Re: Build ready' --body 'Thanks'
agent-mail send --to codemit/coordinator --subject 'Deploy blocked' --body 'Needs a decision' --urgent
agent-mail ack 42
agent-mail complete 42
agent-mail watch --after 0 --json
agent-mail wait --timeout 1800
agent-mail events --after 41 --timeout 25
```

`send` and `reply` accept `--body`, `--body-file`, or piped stdin. `--urgent` sends with priority `urgent` (without it the request carries no priority field, so older servers accept it unchanged; an older server ignores `--urgent` and stores normal mail). Human-readable `inbox`, `outbox` and `read` output prefix urgent subjects with `[urgent]`; `--json` output includes `priority`. `--json` returns machine-readable results for list/read/send/status operations. `watch` is a reconnecting long poll; save its printed cursor and pass it back with `--after` after restarting. Notifications can repeat after reconnect by design.

`wait` checks the inbox for `pending` messages (every `--interval` seconds, default 15), prints them as `#ID sender | subject | task=ID` lines (or a JSON array with `--json`; urgent lines end with ` | urgent`, normal lines are unchanged) and exits 0. It never marks anything read, and it returns immediately when pending mail already exists, so it is safe to run as a background "wake me when mail arrives" step. With no pending mail before `--timeout` (default 1800 seconds, `0` = no limit) it exits 3. Credential errors exit 1 at once; transient network errors are retried.

`events` makes one long-poll request to `/api/events/poll` and prints each event as a `#ID sender | subject | task=ID` line (urgent lines end with ` | urgent`, like `wait`), or the server's `{"events":[...],"cursor":N}` response unchanged with `--json`. `--after ID` resumes after a cursor (default: every pending message) and `--timeout SECONDS` sets the wait (default 25, `0` = answer at once, capped by the server). It exits 0 when events came back and 3 when none did (printing `no new mail (cursor N)` to stderr). It never changes message state.

Every command accepts only its own options; `agent-mail <command> --help` lists them. An unknown command or option, a missing option value, or an invalid `--status` exits with code 2 instead of being ignored. Exit codes: 0 success, 1 error, 2 usage error, 3 `wait` timed out or `events` returned no mail.

Use a separate `--profile NAME` for each local session or role; each profile has its own protected credential file. `--profile NAME` (or `--profile=NAME`) works before or after the command, including `config set`, and takes precedence over `AGENT_MAIL_PROFILE`. A profile named by either must already have a saved config; the CLI exits with an error rather than falling back to the default profile. `AGENT_MAIL_PROFILE`, `AGENT_MAIL_ENDPOINT`, `AGENT_MAIL_ROLE`, and `AGENT_MAIL_TOKEN` can select or override a profile for isolated process environments. **Numbered roles:** a session holding `team/worker-2` with a `team/worker` profile acts as that number with the global `--role team/worker-2` (before the command) or `AGENT_MAIL_ROLE=team/worker-2` (`--role` wins); the value must be the profile's role or `<profile role>-N`, otherwise the CLI exits with usage error 2. (When `AGENT_MAIL_TOKEN` is also set, or the profile has no saved role, `AGENT_MAIL_ROLE` is the role itself, as before.) The server keeps mailboxes of one base apart: reading, acknowledging, completing or replying to mail of `team/worker-2` while the header names `team/worker` or another number answers 403 naming the role to use; nothing is shown and no state changes. The server always derives the sender role from the credential, regardless of caller-supplied message fields. To enroll a role without restarting the server, set the operator-only enrollment credential in the deployment's external `.env`, then run `agent-mail register --endpoint URL --role ROLE --token-file ROLE_TOKEN_FILE --enrollment-token-file ENROLLMENT_TOKEN_FILE`. A role owner can resume with the same role credential; registration cannot replace an existing role credential. Keep the enrollment credential private and rotate or remove it when enrollment is closed.

## Docker deployment

The Compose file binds to loopback by default (`127.0.0.1:8097`). For private network access, set `MAIL_BIND_ADDRESS` in the external `.env` to the intended private interface address; do not bind publicly without a TLS reverse proxy and appropriate network controls. Set `AGENT_MAIL_TOKENS` and, when enabling dynamic enrollment, `AGENT_MAIL_ENROLLMENT_TOKEN` in an external `.env` file with mode `0600`; build and start with `docker compose up -d --build`. The enrollment value is optional so existing deployments continue to start; registration is disabled until it is set. Existing role definitions and message history stay in the SQLite volume. The container runs as nonroot, drops capabilities, has a read-only root filesystem, health check, restart policy, and a named volume. Never put credentials in the Compose file or source control.

### Automated deployment (Actions image + Jenkins)

`docker compose up -d --build` above builds locally (the image is tagged `agent-mail:local`). The production path never builds on the server:

1. A pull request runs `CI` (tests, vet, build).
2. A push to `main` runs `promote`: the same checks in parallel with `image`, which builds `linux/amd64` and pushes `ghcr.io/sandcorporation/agent-mail:<commit sha>`. When both pass, `production` is fast-forwarded to that commit (`scripts/ci/promote.sh`). `production` only moves forward; roll back with a revert PR.
3. A Jenkins job using the `Jenkinsfile` watches `production` only. Through the `sandcorp` shared library (`sandcorpDeploy`) it waits for the GHCR image of the `production` head, pulls it on the node labelled `agent-mail-deploy`, recreates the `agent-mail` service with `AGENT_MAIL_IMAGE` set to that image (`--no-build`), waits for the container health check and runs `/health` inside the container. If the new container does not become healthy it switches back to the previous successfully deployed image. The `ROLLBACK_SHA` job parameter deploys an older published image.

Nothing deploys until such a job exists. Host-specific values are not in this repository: the deploy node is chosen by its Jenkins label, and secrets plus `MAIL_BIND_ADDRESS` come from the `.env` file in the job workspace on that node (mode `0600`, same keys as above), or, optionally, from an env file outside the workspace named by the node's `DEPLOY_ENV_FILE` environment variable. The workspace `.env` is the default; note that Jenkins can wipe the workspace when a checkout fails, so keep a copy of it. The deploy stops before replacing anything if `AGENT_MAIL_TOKENS` or `MAIL_BIND_ADDRESS` is empty. Keep the Compose project name `agent-mail` so the existing `agent-mail_agent_mail_data` volume is reused; moving from a manual deployment only recreates the container. The deploy node needs Docker with Compose and pull access to the GHCR package.

### Protected administrator dashboard

The dashboard shows all messages, sessions and registered role names, and lets the administrator answer questions and edit question settings. Its `/api/admin/*` endpoints return `401` unless `AGENT_MAIL_ADMIN_PROXY_TOKEN` is configured and the request includes the matching `X-Agent-Mail-Admin` header. The browser does not know this value. Configure a separate random secret in the private deployment `.env` and in the service's private reverse-proxy configuration; do not reuse any role or Authelia credential. The proxy must authenticate the browser session with Authelia before forwarding and must overwrite (never pass through) any incoming `X-Agent-Mail-Admin` header with the configured secret. Keep the backend bound to loopback/private networking so clients cannot bypass the proxy boundary. Requests without the secret cannot use admin APIs. Admin writes (`PUT`, `POST`, `DELETE`) additionally need `Content-Type: application/json` and `X-Agent-Mail-Dashboard: 1`, and `Sec-Fetch-Site`, when the browser sends it, must be `same-origin`; otherwise they get `403`. This is CSRF protection: the proxy authenticates by cookie, and the custom header forces a CORS preflight that a cross-site page cannot pass. `GET` needs none of these.

The 지표 tab (`#metrics`, after 세션) reads `GET /api/admin/metrics` for the last 7 or 30 days: first-reply counts, p50/p90/max and a bucket bar chart with a per-recipient table; pending mail per role (rows over the threshold highlighted); the multi-round count and top threads (clicking one opens the 메일 tab filtered to that thread); error/blocked time per role and the sessions in such a state now. Its tab number counts what is over an alert threshold now: flagged pending rows plus current error/blocked sessions past a non-zero limit (hidden when 0).

For nginx, keep your existing Authelia protection on the dashboard host and add this directive inside only this service's already-protected `location /` (substitute the private secret from your secret-management process; do not commit it):

```nginx
proxy_set_header X-Agent-Mail-Admin "<same random value as AGENT_MAIL_ADMIN_PROXY_TOKEN>";
```

This replaces any browser-supplied admin header, while leaving ordinary role-token API requests intact for CLI use. The dashboard itself does not send an `Authorization` header. Validate nginx configuration before reloading it. If Authelia protects only selected paths, also protect `/api/admin/` with the same authenticated session check.

Backup and restore while stopped (SQLite WAL is checkpointed on clean shutdown):

```sh
docker compose stop
mkdir -p backup
docker run --rm -v agent-mail_agent_mail_data:/data -v "$PWD/backup:/backup" alpine sh -c 'cp /data/mail.db /backup/mail.db'
docker compose start
# Restore: stop service, copy a verified backup back to /data/mail.db, then start.
```

Use the actual volume name from `docker volume ls` if Compose prefixes it differently. Retain and protect the token file separately from database backups. For safe online backups use SQLite's backup API or briefly stop the container as above.

## API

All `/api/*` routes except registration require `Authorization: Bearer <role-token>` and `X-Agent-Mail-Role: <expected-role>`. The server checks that the selected role matches the credential, so a session cannot accidentally use another profile's identity. Unauthorized or mismatched requests return 401; a recipient outside the registered role set returns 403. `POST /api/register` accepts `{role,credential}` and requires the operator enrollment bearer credential for new roles. Existing roles may only be resumed by presenting their same role credential.

- `POST /api/messages` with `{recipient,subject,body,task_id?,thread_id?,reply_to?,priority?}`. `priority` is `normal` (default when omitted) or `urgent`; any other value returns 400. Optional `Idempotency-Key` header; a retry returns the first message, including its priority.
- Every message in a JSON response (send, reply, list, read, admin list) includes `"priority":"normal"|"urgent"`. Messages stored before priority existed are `normal`.
- `GET /api/messages?box=inbox|outbox&q=...&status=...`
- `GET /api/messages/{id}`; recipient read marks `read`, sender may inspect own outbox messages.
- `POST /api/messages/{id}/reply` with `{subject,body,recipient?,priority?}` (same `priority` rules as send).
- `POST /api/messages/{id}/ack`, `/complete`; recipient only.
- `GET /api/watch?after=<message-id>` waits up to 25 seconds, returns `{messages:[ids],cursor:id,timeout?:true}`. Replay with the returned cursor. IDs are durable; concurrent watchers independently replay and can see duplicates.
- `GET /api/events` streams new pending mail for the authenticated role as server-sent events (same two auth headers; `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`). Optional cursor: `Last-Event-ID: <message-id>` header, or `?after=<message-id>` (the header wins); a non-integer cursor returns 400. On connect the server sends `retry: 3000`, then a backlog of `event: message` frames, then `event: ready` with `{"cursor":<last id sent or the given cursor>}`, then live `event: message` frames as mail is stored, and `: ping` comments every `AGENT_MAIL_SSE_KEEPALIVE` (Go duration, default `20s`). Each message frame carries `id: <message-id>` and `data: {"id","sender","recipient","subject","priority","created_at","task_id"?,"thread_id"?,"body"?}`; `priority` is `normal` or `urgent` and `body` is present only for urgent mail. Without a cursor the backlog is every message whose recipient state is still `pending`; with a cursor it is pending messages with a larger ID. Within one connection each message is sent at most once, in ID order; reconnecting with the last received `id` never repeats a message at or below it, while reconnecting without a cursor resends whatever is still pending, so clients dedupe by ID. Streaming has no state side effects. Example: `curl -N -H "Authorization: Bearer $TOKEN" -H "X-Agent-Mail-Role: worker" -H "Last-Event-ID: 41" https://mail.example/api/events`.
- `GET /api/events/poll?after=<message-id>&timeout=<seconds>` is the long-poll form of `/api/events` for clients that can only read a complete response (same two auth headers, 401 otherwise). It uses the same cursor rules (`Last-Event-ID` header or `?after=`, header wins; no cursor means every message still `pending`) and returns the same event objects as the stream's `data`, as `{"events":[...],"cursor":N}` with `Content-Type: application/json` and `Cache-Control: no-store`. `cursor` is the ID of the last event returned, or the request cursor (0 without one) when `events` is empty; pass it back as `after`. When pending mail after the cursor exists it answers at once (at most 200 events per response, oldest first; poll again for more); otherwise it waits for new mail for the role and answers as soon as some is stored, or with an empty list when `timeout` passes. `timeout` defaults to 25 seconds, `0` answers at once, and values above `AGENT_MAIL_POLL_MAX` (whole seconds, default `55`, below a typical 60-second proxy read timeout) are capped. A non-integer or negative `after`/`timeout` returns 400. Polling has no state side effects; server shutdown answers waiting polls with an empty list. Example: `curl -H "Authorization: Bearer $TOKEN" -H "X-Agent-Mail-Role: worker" "https://mail.example/api/events/poll?after=41&timeout=25"`.
- **Numbered slots.** A base role (say `team/worker`) can be held by several sessions as `team/worker-1`, `team/worker-2`, … The base role's token authorises every `team/worker-N` (N = 1…999, no leading zeros) in `X-Agent-Mail-Role`; a token of another base gets 401. A role row registered under the exact name (for example a separately enrolled `team/lead-2`) always wins: only its own token works for that name and slot registration skips that number. The number need not be currently leased to authenticate, so mail queued for an expired slot stays readable.
- **`team/worker` and `team/worker-1` are one mailbox.** Mail to the unnumbered base goes to slot 1. It is stored under the base name, so clients that never register (header `team/worker`) and the session holding `-1` see the same inbox, read/ack/complete state, `wait`, `/api/events` and `/api/events/poll` wake-ups; mail sent by `-1` carries sender `team/worker` and `recipient` of mail to `-1` reads `team/worker`. `-2` and above see only their own mail. Mail may be sent to any `-N` of a registered base whether or not it is leased; it waits there.
- `POST /api/slots/register` with `{machine,directory,session_id?,label?,parent?}` (fields up to 512 bytes; `machine` and `directory` required, else 400) assigns a numbered slot under the caller's base, atomically in one SQLite transaction. The same machine+directory gets its previous number back, even before its lease ends; a new identity gets the smallest free number. Response: `{"role","base","number","machine","directory","session_id"?,"label"?,"parent"?,"registered_at","lease_expires_at","lease_seconds","other_active","reclaimed"}`; `other_active` counts the base's other leased slots (for a duplicate warning).
- `POST /api/slots/heartbeat` (same body) extends the identity's lease and updates `session_id`/`label`/`parent`; it answers with the same shape. If a takeover moved the slot, the answer's `role` is the new one. 404 means the identity holds no slot any more (its number was reassigned after expiry): register again. `POST /api/slots/release` (same body) ends the lease now.
- `POST /api/slots/takeover` (same body) gives the caller number 1. A leased previous holder moves to the smallest free number other than 1, keeping its lease, and is reported as `displaced`; an expired holder is dropped. The caller's own previous number is released. 409 when `<base>-1` is a separately registered role.
- Leases last `AGENT_MAIL_PRESENCE_INTERVAL` × `AGENT_MAIL_PRESENCE_MISSED` (default `60s` × `3` = 3 minutes); `AGENT_MAIL_SLOT_LEASE` (Go duration), when set, overrides that product. An expired slot leaves the slot table and its number becomes free; its mail stays queued. Expiry is evaluated lazily when slots are read or assigned. `GET /api/slots` lists the leased slots of the caller's base; `GET /api/admin/slots` (admin proxy only, read-only) lists every base. CLI: `agent-mail slots [--json]` and `agent-mail slot register|heartbeat|takeover|release [--machine NAME] [--directory PATH] [--session-id ID] [--label TEXT] [--parent ROLE] [--json]` (machine and directory default to this host and the current directory).
- **Session presence.** Register, heartbeat and takeover also carry the session's presence: `state` (`idle`, `busy`, `compacting`, `error:<kind>` when the turn failed, e.g. `error:StopFailure`, or `blocked:<kind>` when the session waits on a person, e.g. `blocked:permission_prompt`; `<kind>` is 1–64 characters from `A-Z a-z 0-9 . _ -` and the prefix is lowercase and exact; anything else is 400, and the state is stored and returned verbatim), `context_tokens` (whole number ≥ 0, else 400) and `last_turn_at` (RFC 3339, else 400), all optional. Sessions send a heartbeat when their state changes and every `AGENT_MAIL_PRESENCE_INTERVAL` (Go duration, default `60s`). A heartbeat keeps fields it leaves out; register and takeover start from what they send. One rule decides offline: **a session is offline exactly when its slot lease has ended**, i.e. after `AGENT_MAIL_PRESENCE_MISSED` (default `3`) missed heartbeats, or at once after `release`. The number is then free for others; the same identity reporting again before anyone takes it is online again on the same number (otherwise heartbeat gets 404 and it registers again).
- `GET /api/presence[?role=FILTER]` is readable by any authenticated role (including `<base>-N`) and lists every session; it never contains tokens. `FILTER` is a base (`team/worker`: all its numbers), a numbered role (`team/worker-2`) or a prefix ending in `*` (`team/*`). Offline sessions stay listed for `AGENT_MAIL_PRESENCE_RETAIN` (Go duration, default `24h`, `0` hides them) unless another identity takes the number. Response: `{"now","interval_seconds","missed","lease_seconds","retain_seconds","sessions":[{"role","base","number","online","status","state"?,"context_tokens","last_turn_at"?,"machine","directory","session_id"?,"label"?,"parent"?,"registered_at","reported_at"?,"lease_expires_at","offline_since"?}]}`. `status` is `offline` when not online, else the reported state (verbatim, including `error:<kind>` / `blocked:<kind>`) or `unknown`; `state` keeps the last reported state while offline; `context_tokens` is `null` until reported. `GET /api/admin/presence` (admin proxy only, read-only) answers the same, and the dashboard shows it as the 세션 table (`error:X` as `오류: X` in red, `blocked:X` as `막힘: X` in amber; a long 폴더 is shortened from the front so the last folder stays visible, with the full path on hover).
- CLI: `agent-mail status [ROLE] [--json]` prints `ROLE STATUS CONTEXT LAST TURN MACHINE DIRECTORY LABEL PARENT REPORTED` (context in thousands, e.g. `45k`; reported as time since the last heartbeat on the server clock). `agent-mail slot register|heartbeat|takeover` accept `--state STATE`, `--context-tokens N` and `--last-turn-at TIME`.
- **Label addresses.** Mail may be addressed to `label:<base>/<label>` (for example `label:team/worker/issue-17`) before any session carries that label. `<base>` must be a registered role (else 403); `<label>` is 1–128 characters from `A-Z a-z 0-9 . _ -` (the label is the part after the last `/`); any other `label:` form is 400. If a leased slot of `<base>` has that label (the `label` field of register/heartbeat/takeover), the message goes straight to that slot's mailbox (the smallest number when several do). Otherwise it is **held**: stored with `recipient` `label:<base>/<label>` and `status` `held`, shown in the sender's outbox and the admin list (`box=held`), and in no inbox. The first session of `<base>` that registers, heartbeats or takes over with that label receives every held message for it, atomically in the same transaction (the grant's `held_delivered` counts them), and its event stream or poll wakes. Held mail does not expire. Labels are scoped to the base on purpose: any token can register any label for its own base, so an unscoped label such as an issue number could be collected by a session of another team; sessions of other bases never receive the mail. A moved message gets a **new ID** (so event and watch cursors that already passed the old ID still see it); `held_id` is the ID returned at send time, which no longer resolves. Message JSON (and outbox) shows the final `recipient`, plus `addressed_to` (the label address) for label mail, and `held_at`/`delivered_at`/`held_id` when it was held; event data carries `addressed_to`. CLI: `agent-mail send --to label:team/worker/issue-17 ...`.
- **Stall notices.** The server sweeps every `AGENT_MAIL_SWEEP_INTERVAL` (default `30s`) and sends ordinary (`normal`) mail from the system sender `agent-mail/system`. (1) When a session's lease ends without a release, its presence `parent` gets one notice (subject `offline: team/worker-2`, body like `Session team/worker-2 (label issue-17, machine box-1, directory /work/repo) went offline at 2026-01-01T10:03:00Z; last report 2026-01-01T10:00:00Z.`). No repeats while it stays offline; a session that comes back and goes offline again is noticed again. A release (`POST /api/slots/release`) is an intended stop and sends nothing. No notice is sent when the parent is empty, not a registered role, or the session itself. (2) When mail to `label:<base>/<label>` stays held for `AGENT_MAIL_LABEL_STALL` (default `10m`), its sender gets one notice per label (subject `label not connected: label:team/worker/issue-17`) listing the held message IDs; the mail stays held and is still delivered when the label connects. Notices never contain tokens.
- **Mail-flow metrics.** `GET /api/metrics[?days=N]` (boss roles in `AGENT_MAIL_BOSS_ROLES` only, everyone else 403) and `GET /api/admin/metrics[?days=N]` (admin proxy only) answer the same JSON for the `N` days (1–90, default 7, else 400) ending now: `{"window":{"from","to","days"},"first_reply":{"count","answered","unanswered","p50_s","p90_s","max_s","buckets":[{"label","up_to_s","count"}],"by_recipient":[{"base",…same counts}]},"pending":[{"role","pending","oldest_s","over_threshold"}],"threads":{"multi_round","top":[{"thread_id","subject","parties","round_trips"}]},"sessions":{"by_role":[{"role","error_s","blocked_s","top_kinds":[{"state","seconds"}]}],"current":[{"role","state","since","seconds"}]},"thresholds":{"pending_s","error_s","blocked_s"}}`. **First reply** covers mail from a non-system sender that starts a thread (no `thread_id`/`reply_to`, and no `task_id` an earlier message in the window already carried); its latency is the time to the first later message in the same thread, or with the same non-empty `task_id`, sent by the recipient's base back to the sender's base (any numbered slot counts for its base). Unanswered mail is counted but is no latency; percentiles are nearest-rank and `null` when nothing was answered; buckets are `<10m`, `<1h`, `<4h`, `<1d`, `>=1d`. **Pending** is the mail pending now per recipient role, without `agent-mail/system` mail, oldest first. **Threads** counts, for each thread in the window, direction changes between its two most frequent bases (A→B→A→B is 3 changes); round trips = changes / 2 rounded down; `multi_round` is the number with ≥ 2 and `top` the 10 largest. **Sessions** is the time each numbered role spent in `error:*` / `blocked:*`, clipped to the window, with its 3 largest kinds, plus the online sessions in such a state now. Every state change is logged in `presence_log` (kept 60 days). Thresholds: `AGENT_MAIL_ALERT_PENDING` (default `2h`), `AGENT_MAIL_ALERT_ERROR` (`10m`), `AGENT_MAIL_ALERT_BLOCKED` (`30m`), Go durations, `0` disables. CLI: `agent-mail metrics [--days N] [--json]` prints a compact summary. **Alerts:** the 30s sweep mails every boss role in `AGENT_MAIL_BOSS_ROLES` (normal priority, from `agent-mail/system`) when a role has pending non-system mail older than the pending threshold (one alert per recipient role; a boss is not told about mail pending for its own base), or an online session has been in `error:*` / `blocked:*` longer than its threshold (one per session role). Each `(kind, role)` alerts at most once per UTC day. Subject `[지표] pending <role> 3통, 가장 오래 2h40m` or `[지표] error <role> <state>, 12m째`; the body points to `agent-mail metrics` and the dashboard `#metrics` tab; `task_id` is `alert:<kind>:<role>:<YYYY-MM-DD>`.
- **System sender.** `agent-mail/system` (and `agent-mail/system-N`) is reserved: nobody can authenticate as it, even if a role row or `AGENT_MAIL_TOKENS` entry with that name exists (such entries are ignored), `/api/register` refuses it with 403, and mail to it is refused with 403 like an unknown role.
- **Permission requests.** `POST /api/permissions` with `{tool,summary}` (`tool` 1–128 bytes, `summary` 1–500 bytes, else 400) creates a request and answers 201 with `{id,requester,tool,summary,parent?,ignored_parent?,status,decision?,note?,answered_by?,created_at,expires_at,answered_at?,can_answer}`. `id` is server-issued and opaque (`perm_…`); `status` is `pending`, `allowed`, `denied` or `expired`; requests expire after `AGENT_MAIL_PERMISSION_TTL` (default `10m`). The **parent** is the `parent` on the requester's active slot at request time and stays fixed on the request. Only a role in `AGENT_MAIL_BOSS_ROLES` (comma-separated bases or exact roles, empty by default) may answer; the requester's own base never may, even when it is a boss. The parent cannot answer: sessions on one machine can read each other's profile files, so only a boss, whose credential lives on a separate machine, is an independent check. A parent of the requester's own base (itself or a sibling slot) is ignored (`ignored_parent`), because any holder of the base token can act as every `<base>-N`. When no boss of another base is registered (or `AGENT_MAIL_BOSS_ROLES` is empty), the request is refused with 409 "nobody can answer", even when a parent exists, and the session falls back to its local prompt. Every boss of another base receives an **urgent** mail with the summary, request ID and the `permission answer` command; a trusted parent also receives an **urgent** mail that says a boss must answer and has no answer command (both with `task_id` = request ID).
  - `POST /api/permissions/{id}/answer` with `{decision: "allow"|"deny", note?}` (note up to 500 bytes): 200 with the request, 400 bad decision, 404 unknown ID, 403 caller may not answer (anyone but a boss of another base, the parent included), 409 already answered, 410 expired. The requester receives an **urgent** mail (`permission allowed: Bash` / `permission denied: Bash`, `task_id` = request ID).
  - `GET /api/permissions/{id}` (requester's base, parent or boss; else 403, unknown 404) and `GET /api/permissions[?pending=1]` (requests of the caller's base and those it is parent of or may answer, newest 100; `can_answer` marks the ones the caller can answer now).
  - CLI: `agent-mail permission request --tool NAME --summary TEXT`, `permission show ID`, `permission answer ID --decision allow|deny [--note TEXT]`, `permission list [--pending]`, each with `--json`.
- **Question settings** (admin proxy only). Per-role settings for remote questions: `can_ask`, `watchers` (up to 20 role names) and `discord`. A target is `default` (always present, created as `can_ask=false, watchers=[], discord=false`, cannot be deleted), an exact role such as `svc/coordinator` (it also covers `svc/coordinator-N`), or a prefix such as `svc/*` (every role starting with `svc/`). A role resolves to its exact entry (after stripping `-N`), else the longest matching prefix, else `default`.
  - `GET /api/admin/question-settings` returns `[{target, can_ask, watchers, discord, updated_at}]` with `default` first.
  - `PUT /api/admin/question-settings/{target}` with `{can_ask, watchers, discord}` (missing fields are `false`/`[]`, duplicate watchers are dropped, unknown fields are 400) creates or replaces the entry and returns the row. `DELETE /api/admin/question-settings/{target}` removes it (`default` is 400, a missing entry 404). An invalid target or watcher name, or more than 20 watchers, is 400. Both writes need the admin write guard above.
- **Questions.** `POST /api/questions` with `{questions:[{header,question,options:[{label,description,preview?}],multiSelect}]}` asks 1–4 multiple-choice questions (each with 2–4 options; `header` 1–12 characters, `question` 1–1000 bytes, `label` 1–100 bytes and unique within its question, `description` up to 500, `preview` up to 4000; the whole body at most 32 KiB; else 400). It answers 201 with the question view `{id,asker,created_at,status,questions,answers,answered_by,answered_at,withdrawn_at,seq,can_answer}`: `id` is `q_` + 32 hex characters, `status` is `pending`, `answered` or `withdrawn`, `answers`/`answered_at`/`withdrawn_at` are `null` and `answered_by` is `""` until they apply, and `seq` is a global change counter bumped on create, answer and withdraw. The asker must have `can_ask` in its resolved question settings (else 403), and a boss role of another base must be registered (else 409 "nobody can answer"). Watchers from the asker's resolved settings (other bases only, unknown roles skipped) get a normal mail `[질문] <id> <asker> <first header>` with the questions and options, followed by a 「관련 지난 결정」 block when there are related decisions (below); bosses are not mailed and poll instead. The 201 body also carries `related`: up to 3 past decisions — the asker base's own, newest first; then, when the asker's resolved settings target is a `<prefix>/*` row, other bases under that prefix; then any whose first header equals the new first header (ASCII case-insensitive). These may come from other bases.
  - `POST /api/questions/{id}/answer` with `{answers:[{selected:[label…],other?}]}`, one entry per question in order: labels must be options of that question, a single-select question takes at most one, `other` is up to 1000 bytes, and each entry needs a label or `other` (else 400). Only a boss of a base other than the asker's may answer (else 403, unknown ID 404); the first answer wins and later ones get 409, as does an answer to a withdrawn question. 200 with the view. The asker gets a normal mail `[질문 답] <id> <first header>` (`task_id` = id) with one line per question, `<header>: <question> = <labels>` plus ` / 기타: <other>`, then `답한 쪽: <role>`; watchers get the same text as `[질문 답] <id> <asker> <first header>`.
  - `POST /api/questions/{id}/withdraw`: only the asker's base (else 403); 409 when not pending; 200 with the view. No mail.
  - `GET /api/questions/{id}` (the asker's base or a boss; else 403, unknown 404) and `GET /api/questions[?status=pending|answered|withdrawn][&limit=N]` (`{questions:[…]}`, newest first, default 100, at most 500; bosses see every question, other roles their own base's; `can_answer` marks the ones the caller can answer now).
  - `GET /api/questions/poll?after=<seq>&timeout=<seconds>` long-polls like `/api/events/poll` (default 25 s, capped by the server): `{questions:[views with seq > after visible to the caller, oldest change first],cursor:N}`, where `cursor` is the highest `seq` returned, or `after` when nothing is. It answers at once when there are changes. A question appears again whenever it changes, so a panel can close items answered or withdrawn elsewhere.
  - Admin (proxy secret; the answer also needs the admin write guard): `GET /api/admin/questions[?status=pending|answered|withdrawn][&limit=N]` returns `{questions:[…]}` with every question, newest first (default 100, at most 500); without a status the pending ones come first. `can_answer` is true for every pending question. `POST /api/admin/questions/{id}/answer` with `{answers:[…]}` answers through the same core and validation as the role endpoint with `answered_by` = `dashboard`: no boss check, but 409 when the question is no longer pending (404 unknown, 400 bad answers); 200 with the view. The asker and watchers are mailed as for a role answer.
  - Dashboard: the 질문 tab lists the questions (count of pending ones on the tab) with an answer form per pending question (radio buttons for single-select, checkboxes for multiSelect, a 기타 text field; previews in `<pre>`); a 409 shows 「이미 답했거나 거둔 질문입니다」 and reloads. `#q=<id>` opens the tab and scrolls to and highlights that question. The 설정 tab lists the question settings and edits them (PUT), with a delete button on rows other than `default`.
  - **Decisions.** A decision is an answered question: `{id,asker,asked_at,answered_at,answered_by,items:[{header,question,chosen:[label…],other}]}`. `GET /api/decisions` (a boss sees all, other roles their own base) and `GET /api/admin/decisions` (proxy secret, everything) take `from`/`to` (a date `YYYY-MM-DD`, UTC day, `to` inclusive; or an RFC 3339 time) on `answered_at`, `role` (an exact role or base, or `<prefix>/*`), `q` (case-insensitive substring of a header, question or chosen label) and `format=json|ndjson`; bad values are 400. Newest answer first, at most 1000. JSON is `{decisions:[…]}`; `ndjson` is one decision per line with `Content-Disposition: attachment; filename="decisions-<from>-<to>.ndjson"` (`start` / today's UTC date when unset). The dashboard's 질문 tab has a 「질문 | 결정」 switch: the 결정 view lists decisions (asker, time, header → chosen) with period (7/30/90 days, all, or custom dates), role and text filters, and a 「JSON 내보내기」 link that downloads the filtered ndjson. `#decisions` opens it.
  - CLI: `agent-mail question ask --file Q.json`, `question show ID`, `question list [--status S]`, `question answer ID --file A.json`, `question withdraw ID`, each with `--json`. The files hold `{"questions":[…]}` / `{"answers":[…]}` or just the list.
  - **Discord notice.** When `AGENT_MAIL_DISCORD_WEBHOOK` is set and the asker's resolved settings have `discord=true`, each new question posts one line to that webhook after it is stored: `질문 <id> · <asker> · <first header> <AGENT_MAIL_PUBLIC_URL>/#q=<id>` (the link is left out when `AGENT_MAIL_PUBLIC_URL`, the dashboard base URL such as `https://mail.example`, is unset). The question text and options are never sent, and `allowed_mentions` is empty so names cannot ping anyone. `AGENT_MAIL_DISCORD_USERNAME` and `AGENT_MAIL_DISCORD_AVATAR_URL` (must start with `https://`, such as `https://mail.example/avatar.png`; otherwise ignored with a log line at start) set the bot name and avatar; when empty the webhook's own defaults apply. The notice is sent in the background with a 5 s timeout; a failure only logs `discord notice failed: <status or error class>` and never changes the 201 response. The webhook URL is a credential: keep it in the external `.env`; the server never logs it.
- `GET /health` is unauthenticated and returns `{ok:true}`.
- `POST /api/register` durably registers a new role without a service restart, or verifies credential ownership to resume an existing role.

Orca integration belongs in a separate wake/session adapter. This service has no Orca terminal handle dependency and cannot start a stopped session. An adapter may poll/watch and route a role notification to an available session; mailbox durability and explicit acknowledgment remain authoritative.

## Install and uninstall CLI

GitHub Actions builds versioned archives for Windows, Linux, and macOS (amd64 and arm64 where supported), plus SHA-256 checksums. Download the archive for your platform from Releases, verify `checksums.txt`, and place `agent-mail`/`agent-mail.exe` on PATH. Configure the endpoint, role, and token as above. Config is stored at the OS user config directory under `agent-mail/config.json` with user-only permissions. To uninstall, remove the binary and that config directory; removing config deletes the local token copy. Server messages remain until the operator removes the service volume.

## Tests and limitations

Run `go test ./...`. Current tests cover SQLite persistence across database reopen, retry idempotency, auth rejection, watch cursor replay, status filtering, the event stream (role isolation, pending backlog, `Last-Event-ID` resume, keep-alive, shutdown), the long poll (immediate answer, wake on send, timeout, cursor resume, server cap, disconnect and shutdown, 400/401, the `events` CLI command), message priority (defaults, validation, urgent event bodies, reply, CLI markers, old-server compatibility), numbered slots (concurrent registration, identity reclaim, takeover, prefix tokens, lease expiry, unnumbered/`-1` mailbox sharing, the `slot`/`slots` commands), session presence (report and query, field validation, offline after missed heartbeats with the lease released, back online, retention, settings, the `status` command), mail-flow metrics (first reply by thread and task_id, unanswered not a latency, pending without system mail, round trips, window clipping, presence_log open/close and pruning, boss-only endpoint, the `metrics` command), metrics alerts (each kind once per UTC day and again the next day, `0` disables, offline sessions and a boss's own pending mail skipped, 30-day pruning), stall notices (offline once per transition, none after release or without a usable parent, label stall once per held message, concurrent sweeps, sweeper shutdown), the reserved system sender, permission requests (boss answers, parent informed but 403, third party/requester/sibling 403, 409 without a boss even with a parent, same-base parent ignored, parent fixed at request time, 404/409/410, concurrent answers, the `permission` command), label addresses (holding, delivery on register/heartbeat/takeover with stream and poll wake-ups, direct delivery to an active session, concurrent registrations, base scoping, address validation, idempotent retries) and the in-place schema migration of pre-priority, pre-presence, pre-label and pre-permission databases. This first release uses a single SQLite writer, bounded newest-first listing, basic substring search, bearer tokens without token rotation UI, and long polling plus a server-sent event stream (`/api/events`, with the `/api/events/poll` long-poll companion) whose subscribers live in one server process. Back up the data volume and restrict network access to private/Tailscale paths.
